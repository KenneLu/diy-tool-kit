# 公共规范

> 适用于 diy-tool-kit 家族的工具（含新工具与发生实质变更的既有工具）；历史既有工具按 `迁移与工具对照.md` 的 legacy 例外处理，不追溯判红。以下是共性底线，托盘/GUI 专属与 CLI 专属要求见 `工具类型/`。
> 工具类型专属要求见 `工具类型/`；本文件与类型文档冲突时以本文件为准。

## 1. 立项与分级

新工具开始前必须记录：

- 工具标识（`APP_ID`）、显示名、版本；
- 主类型：托盘工具 / 命令行工具；
- 是否常驻、是否有 GUI、是否有更新器、是否有本地服务、是否有 SSH 隧道；
- 用户数据目录、配置、日志位置；
- 交付形态：PyInstaller onedir（最终用户主路径）、源码（开发/重建）、安装器（如需要）；不得把“仅源码、用户自备 Python”作为最终用户交付；
- 不采用项及原因。

### 1.1 不采用也要记原因

模板模块、构建步骤、发布要求中不采用的部分，必须在工具仓文档中登记：

```text
项目：update_helper
结论：不采用
原因：无远程更新器，当前手动发布
触发条件：建立远端发布 + 自更新需求时再接入
```

不能因为“当前用不到”而静默缺失；否则后续读者无法判断是漏做还是有意为之。

## 2. 目录与代码职责

一级目录白名单：

```text
src/       应用代码、入口、可导入模块、实现功能的脚本
tests/     测试
resources/ 只放非代码资源（图标、图片、字体、schema、静态数据）
scripts/   构建、发布、维护自动化
docs/      文档
skills/    提示词/技能资源（如有）
```

说明：`release/`、`build/`、`dist/`、`.cache/`、`log/` 等是生成/运行目录，不参与“源码一级目录”白名单；`locales/`、`bin/`、`asr-modules/`、`tools/` 等类型目录必须在工具 README 中解释职责，不得藏客户数据或与声明不符的代码。

要求：

- 所有可执行代码住 `src/`，一级目录不得出现 `.py`；
- `resources/` 不得放 `.py`、`.js`、`.mjs` 等代码；
- 纯代码工具脚本归 `src/`，不要放 `resources/` 或根目录；
- `docs/` 只放文档，不放程序运行时读取的技能/脚本资源；
- 新工具与实质变更工具统一使用 `docs/`；`docs/` 是家族统一约定（MkDocs 等生态也默认 `docs`），不是行业强制。既有工具迁移状态见 `迁移与工具对照.md`。多语言放 `docs/en/`、`docs/zh/`；
- 既有工具的 `doc/` 迁移状态见 [迁移与工具对照](迁移与工具对照.md)；未迁移工具必须登记迁移计划，不得把“没有 docs”当作新工具默认；
- `skills/` 等运行时资源独立于 `docs/`；
- `samples/` 不作为产品内置示例；产品示例/真实项目数据不得进仓库；测试数据放 `tests/fixtures/`，且不得冒充实项目；

## 3. 参数卡与共享模块

- 工具差异只住工具自持的 `src/app_params.py`；
- 共享模块通过 `src/template/` git submodule 复用，import 面为 `template.*`；
- 不得在工具内复制公共模块后再私改；
- 不采用模板模块要按 §1.1 登记原因；
- 共享件升级按模板库版本/借条检查处理，不在工具仓临时打补丁。

## 4. 用户数据、配置、日志

- 用户数据区必须在安装目录之外：
  - Windows：`%LOCALAPPDATA%\<APP_ID>\`；
  - Linux：`$XDG_DATA_HOME/<APP_ID>/` 或 `~/.local/share/<APP_ID>/`；
- 配置、日志、运行时状态不得写进安装目录；
- 如果工具有“项目”概念：项目数据属于项目，不属于工具；项目必须在工具安装目录之外；
- 如果工具有“项目”概念：生成物只写项目内约定目录（例如 `.render/`）或用户明确指定的输出；
- 工厂配置示例可以随工具分发；发布目录中的 `config.json` 只能是工厂示例/首次启动种子，不得包含用户实际配置或凭据；用户配置首次启动时播种到用户数据区；
- 日志不得记录凭据、客户数据或不应长期保留的敏感内容。

## 5. 双语与文档

- 所有面向用户的文档必须中英双语；README/CHANGELOG 可以满足小型工具的文档要求，不强制创建空的 docs/；
- README 至少包含：定位、安装/运行、核心用法、数据边界、构建方式；
- 文档目录使用 `docs/en/`、`docs/zh/`；
- 文档中的命令必须可复制执行，路径使用占位符或相对路径；
- 文档不得出现固定机器绝对路径、个人用户名、内部项目名、客户名；
- 文档、README、CHANGELOG、LICENSE 必须完整、自含；
- 历史内容保留时加明确历史标识，不得伪装成当前能力。

## 6. 构建门禁

默认构建流程：

```text
参数卡/版本一致性检查
→ 编译检查
→ 测试
→ PyInstaller onedir 打包
→ 发布目录内容检查
→ 冻结 exe 冒烟
```

要求：

- 构建必须能在无交互参数下运行（如 `nopause`）；
- 测试失败、版本不一致、打包失败、冒烟失败都必须返回非 0；
- 构建脚本不得硬编码个人/本机路径；可以使用 `%CD%`、`%~dp0` 等运行时派生路径；
- 构建产物不得包含 `samples/`、`tests/`、缓存、日志或用户数据；
- 具体构建入口以工具类型文档为准；`build_release` 模块 README 只解释脚手架，不覆盖规范。

## 7. 打包与发布布局

默认使用 **PyInstaller onedir**：

```text
release/<name>-<version>/
  <name>.exe
  _internal/            # 自带 Python 运行时
  docs/                 # 如随包分发
  skills/               # 如工具有运行时技能资源
  config.example.json
  README.md
  README.zh-CN.md
  CHANGELOG.md
  LICENSE
```

要求：

- 最终用户主路径是打包 exe，**目标机器不需要安装 Python**；
- exe 在发布根目录，不得再套一层 `<name>/`；
- `_internal` 中自带运行时，不在目标机器依赖系统 Python；
- 源码运行是开发/重建方式，不是最终用户唯一方式；
- 构建标志由工具类型决定：命令行工具 `--console`，托盘/GUI 工具 `--noconsole`；
- 发布目录不含项目数据、样例、测试或用户配置；
- 发布包是否签名、是否提供安装器，由发布阶段决定并登记；
- PyInstaller 不是防篡改方案；需要真实性/完整性时使用代码签名、哈希清单和受控发布渠道；未签名对外分发的实际拦截风险需登记；
- onedir 是家族默认：易调试、启动快、目录可审计；onefile/安装器只在有明确分发需求时升级，并写取舍理由。

## 8. 测试与验收

- 测试覆盖：数据结构、错误路径、确定性、边界、打包冒烟；
- 单元测试全绿只是**前置证据**，不能代替用户功能验收；
- 验收必须包含真实使用路径；有项目概念的工具用真实项目，无项目概念的工具用真实输入/真实用户流程；不能只用合成夹具；
- 功能验收与架构验收分开记录；
- 发布前必须重跑构建、测试、冻结 exe 冒烟；
- 证据包含命令、退出码、版本、产物指纹、结果和限制；
- 无法由工具自证的内容（例如外部 MCP 客户端、浏览器点击、设计平台能力）必须标注证据来源和未验证边界。

## 9. Git、脱敏与版本

- 仓库、分支、tag、发布策略必须在工具文档中写明；
- 私有仓库不得在文档中暗示公开开源发布；
- 构建产物、缓存、用户数据、release 目录按 `.gitignore` 排除；
- 版本唯一事实源是 `src/app_params.py`（或约定位置）；
- 首个提交、模板库推送、CI/CD、正式发布必须由用户明确授权；
- 未经授权不得 commit、push、tag、发布。

## 10. 协作与复核

- 每份结论自报快照基线（时间、文件、指纹）；
- 修改共享件优先于修改消费方；未采纳分歧登记“吸收义务”；
- 复核必须独立于施工方；无法分离时更换路由；
- 结论必须带证据；不可核验的自述要显式声明；
- 复核至少两路：技术/交付 + 格式/可读性；高风险再加红队；
- 记录“必须修 / 建议修 / 记录接受”，不能用“已关注”代替关闭。

## 11. 工具类型差异表

| 维度 | 托盘工具 | 命令行工具 |
|---|---|---|
| 常驻 | 通常常驻 | 按需运行，结束即退出 |
| 托盘/GUI | 必须/通常有 | 默认没有 |
| 开机自启 | 常驻场景需要 | 默认不适用 |
| 更新器 | 常见 | 可选，发布阶段决定 |
| 构建标志 | `--noconsole` | `--console` |
| 发布 exe | 必须 | 应提供；用户不装 Python |
| 输入输出 | GUI/托盘 | stdout/stderr/退出码 |
| MCP | 可选/服务型 | 可选，stdin/stdout |
| 图标 | 通常需要 | 可选 |
| 服务/隧道 | 按需 | 通常不适用 |

没有出现在表里的能力，按“主类型 + 登记例外”处理。

## 12. 类型差异与不采用登记

新工具必须填写，不允许“没写就是默认适用”。

| 项 | 状态（adopt / partial / N/A） | 原因 | 触发条件 | 负责人 | 日期 | 证据 |
|---|---|---|---|---|---|---|
| 托盘/GUI |  |  |  |  |  |  |
| 开机自启 |  |  |  |  |  |  |
| 更新器 |  |  |  |  |  |  |
| 服务/隧道 |  |  |  |  |  |  |
| 项目工作区 |  |  |  |  |  |  |
| MCP |  |  |  |  |  |  |
| docs 目录 |  |  |  |  |  |  |
| skills |  |  |  |  |  |  |
| 打包 exe |  |  |  |  |  |  |

状态说明：

- `adopt`：采用并纳入门禁；
- `partial`：部分采用，必须写范围；
- `N/A`：不适用，必须写原因和未来触发条件；
- 不允许空着。

## 13. bat/cmd 字节纪律

- `.bat` 使用 ASCII，避免机器代码页导致中文/特殊字符损坏；
- 统一行尾（仓库约定 CRLF 或 LF 之一），不得混用；
- 不得包含 TAB 字符；
- 不得写入 `/dev/null` 这类 Unix 路径给 cmd；
- 构建后必须读回字节验证，不能只靠“看起来对”；
- 版本/路径/变量中的引号、百分号、延迟展开要按 cmd 规则处理。

## 14. Model Context Protocol 契约

- 工具侧协议适配只保留一个平铺入口 `src/mcp_app.py`；
- 不得在工具内新建 `mcp/` 或 `mcp_template/` 目录；协议层由模板 `mcp_kit` 提供；
- MCP 工具/提示词/资源清单必须可列举、可读取，并有测试；
- CLI 类型默认使用 stdio，不监听端口；HTTP/隧道型 MCP 属于服务型/托盘型，必须在类型文档中说明；
- 资源 URI 是稳定协议标签，不要求与文件路径一一对应；
- 不得把外部平台能力（浏览器、设计平台）宣称为本工具 MCP 能力。

## 15. skills 资源

- `skills/` 是工具运行时/提示词资源，不是文档；
- 不得放在 `docs/` 下；
- 随包分发时 `skills/` 在 release 根目录；
- 每个技能至少包含 `SKILL.md`，文件名稳定；
- 技能内容变更要有版本/变更记录；发布包含清单检查；
- 不采用 skills 的工具在类型差异表登记 `N/A`。

## 16. 发布附件

正式发版至少明确：

- release 目录结构；
- 是否附 zip；zip 的 SHA256；
- 是否生成 BUILD-INFO / BUILD-VALIDATE；
- tag 规则和版本语义（semver 或项目约定）；
- CI 触发条件；
- 发布物中是否包含 docs/skills/config.example；
- 不采用项登记原因。

## 17. 文档语言范围

- 模板规范本身可以使用中文；它是维护者内部规范；
- 工具面向用户的 README/docs 必须中英双语；
- 内部规范引用到工具文档时，不得把内部规范当作产品文档分发；
- 用户文档不得出现固定绝对路径、内部项目名、客户名或个人目录。
