## 二、五个主题分组（**任务之间的关系**）

本波 63 条不是一条流水线，而是**五个并行主题**。理解它们的分工，比逐条读更省时间。

### 主题 1 · 收敛主线（`#1`–`#13`）——**"定义什么叫做对了"**
把四个工具的功能逐项拆开，分成三类：**(a) 业务无关、可直接复用**、**(b) 同格式不同内容**、**(c) 纯业务需解耦**，
据此产出 `ALIGNMENT.md`（对齐表）与"以 reme 为基准"的分歧判定表。
**产出物**：`ALIGNMENT.md` / `CONFORMANCE.md` 的三级对照表。

### 主题 2 · 缺口修复（`#15`–`#38`，最大的一批）——**以"一个具体缺陷"为单位**
每条 = 一个可复现的故障（工具打不开 / 弹窗仍中文 / 门禁假红 / 自启死链 / 更新链不安全…）。
**这批的共同形态**：缺陷都有"**失败不留痕迹**"的性质 —— 门禁全绿而事情是坏的。
⇒ 所以修完**必须配主题 3**。

### 主题 3 · 判据建设（`#16 #20 #21 #29 #33 #35 #43 #49 #50 #57 #60`）——**把"人记得"变成"机器查"**
把主题 1 的规范条款、主题 2 的修复结论，落成 `conformance_check.py` 里的机械条款（`C-xx`）
或 `sync_check.py` 里的漂移判据。
**这批的价值密度最高**，因为它防的是"**下次又错一遍**"。
⚠ 本主题有一类专属缺陷：**判据自己说谎**（假红/假绿/空真），见 `#29 #33 #43 #50`，
产物是 `STANDARDS.md §D7`（观测工具纪律）与 `§D8`（证据与锚纪律）。

### 主题 4 · 发布与构建（`#19 #30 #39 #48 #62 #63 #64`）——**产物真的能跑、且不打扰用户**
门禁可达性（`#19` bat 被 TAB 写坏 ⇒ **测试门禁从未执行**）、
bat 危险顺序（`#30` 空 STAGE 会清空安装目录且无法自动恢复）、
级联重拷（`#39`）、重建与新鲜度口径（`#48 #62`）、自启一致性（`#63 #64`）。
⚠ **红线**：构建不得影响用户正在使用的服务。

### 主题 5 · 调度与冻结（`#40 #48 #51`）——**让上面四个主题不互相撞车**
`#40` 模板大冻结、`#48` 批次主台账、`#51` 依赖图 + **反死锁检查**。
**本波实测过一次真实死锁**：两方各自据一句话在等对方先动，停摆约一小时，根因是"**没有一条能被复核的冻的判据**"。
⇒ 结论进了 `STANDARDS.md §D8` 第 3 条。

## 三、核心思路例程（**项目的"心跳"**）

```
发现分歧
  → 判定（业务冲突？还是"有更好做法"？）
      · 没有这个功能 ⇒ 不算冲突，算【缺口】，必须补
      · 有更好做法   ⇒ 可暂时独立，但必须说明理由
  → 决定改哪一侧（默认以 reme-helper 为基准，但基准 ≠ 正确）
  → 修模板（优先，让它惠及四家） 或 修工具
  → 补判据（否则下次还会错；且判据要带负控：0 命中 vs 没东西可命中必须可区分）
  → 构建 + 冻结（判据 = git status 为空）+ 产出带判据身份的回执
```

**两个必须记住的推论**：
- **差异都带后续义务**：允许的差异，都要考虑"优化模板把它吸收掉"。
- **判据自身也要被检验**：`#29 #33 #43 #50` 四条全是"判据说谎"，
  处置一律是 **先验仪器，再验被测**。

## 四、关键决策记录（**为什么当初这么定**）

> 只记"会影响后续判断"的决策。带**理由**，不带理由的决策在下一个人手里会变成教条。

| # | 决策 | 理由 / 代价 |
|---|---|---|
| D1 | **拷贝式模板**，不是包管理 | 四个工具各自独立打包 exe，无运行时依赖；代价 = 必须靠 `sync_check` 逐字节比对，且**只覆盖被拷贝的那部分**（各仓手写部分没有正本可比 —— `STANDARDS.md §J` 抬头） |
| D2 | 文档三分工：`STANDARDS`（必须做什么）/ `CONFORMANCE`（做到没有）/ `ALIGNMENT`（谁对齐谁） | 规范与实现冲突以 `STANDARDS` 为准；文档与磁盘冲突改文档或改代码，**禁止并存** |
| D3 | **以 `reme-helper` 为基准**判分歧 | 它是最老的蓝图。**但基准 ≠ 正确** —— 本波已在它身上找到两处缺陷（退出框 6 处硬编码中文、`win.title` 用裸常量） |
| D4 | **版本号只在发版时改**；开发期写 `## Unreleased` | `l-s2t` 的 `1.4.1`、`dsh` 的 `1.8.2` 都是"未发版的构建"留下的目录 ⇒ 收敛方向是让引用回到 `VERSION` 那一版 |
| D5 | **"冻"的唯一判据是 `git status --porcelain` 为空** | 不是任何一方的描述（本波因两句话停摆一小时） |
| D6 | **锚 = `(commit, path, blob)`，从不取工作树哈希** | 工作树哈希寿命 < 5 分钟（实测） |
| D7 | **失败方向一律"放行"**（`D3.2`） | 守卫自身出错时"少一层保护"远好于"工具打不开" |
| D8 | **冒烟用探针，不用真守卫**（`D3.3`） | 真守卫遇用户常驻实例会弹**模态**框 ⇒ **无人值守构建被挂死**（比失败更糟） |
| D9 | **红线：构建不得影响用户正在使用的服务**；**最优满足方式是"一个字节都不写"** | 任何需要还原的操作都新增"忘记还原"这一失败模式 |
| D10 | 红线措辞限定为**"拥有服务面的工具"**（dsh / ocx / reme） | `l-s2t` 没有服务面，但其 `stop_service` 会被人误读（见 `HANDOFF §4.1`） |
| D11 | **rename-preserve 优先于删除** | 保留 = 保留回滚路径；代价 = 被 Run 键指向的路径会短暂消失（ocx 实测 ~1 分钟） |
| D12 | **仪器错比被测物错更贵** | 判据说谎会把整轮努力导向错误的修复对象，甚至诱导人去改**本来是对的**东西 |
| D13 | `reme` **不采纳** `update_helper` | 它是蓝图；反向采纳会毁掉唯一的基线。**代价已知**：一致性靠人工审阅维持（实证：reme 早就把外部命令绝对路径化了，而模板很久之后才追上，**其间没有任何机制报告过**） |
| D14 | `C2` 落点 = **`tray_kit`**（不是 `paths`） | `tray_kit.py` 已有 ctypes + `CreateMutexW` ⇒ **与 `acquire_single_instance` 同族**（进程寿命内核对象守卫、都失败放行）；**同族共处 > 语义归属**。形式 = **迁移**已实测实现，**不引入第二实现** |
| D15 | **分支表一格只能有一个分支** | 一格写两个"或"，执行者必然选错 —— 这是表的缺陷，不是执行者的疏忽 |
| D16 | **"只发生一次"的动作第一次就要全量落盘** | 只 `tail` 尾部 ⇒ 拿不到证据 ⇒ **被迫重跑一次不可逆动作** |
| D17 | **手工登记表必须让位于文件头** | "文件已自带的事实，不要再手抄一份" —— 手抄副本必然滞后（本波实测 3 行） |
| D18 | **`__init__.py` 的 `TEMPLATE-VER` 是该文件自己的版本**，不是模块版本 | 它比同名主件低是常态；拿它判"落后"会得到**看起来有据、实际完全错误**的结论 |
